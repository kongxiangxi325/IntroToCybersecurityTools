# 学科综合讲座实验作业

本仓库用于发布和提交学科综合讲座实验作业。请先阅读本文档，再同步题目、完成作业并发起 Pull Request（以下简称 PR）。

> **最重要的原则：学生只能修改自己“学号姓名”文件夹内的内容，不能修改仓库中的其他任何位置。**

## 1. 仓库目录结构

```text
repo/
├── homework/                  # 老师发布的作业题目及要求
│   ├── Lab1/
│   │   └── Lab1.md
│   └── Lab2/
├── 学号姓名/                   # 每位同学自己的文件夹
│   ├── Lab1/
│   │   ├── 作业文件.c
│   │   └── 说明文件.md
│   └── Lab2/
└── README.md
```

学生文件夹必须位于仓库根目录，名称为“10 位数字学号 + 姓名”，中间不能有空格，例如 `2023010102刘西莹`。

## 2. 学生作业提交流程

### 2.1 第一次配置（只需执行一次）

fork 并 clone 仓库后，绑定老师的仓库地址，以便后续同步新作业：

```bash
git remote add upstream https://github.com/LiuXiYing/IntroToCybersecurityTools.git
```

运行以下命令检查配置：

```bash
git remote -v
```

看到类似以下内容即表示配置成功：

```text
origin    https://github.com/你的账号/仓库名.git (fetch)
origin    https://github.com/你的账号/仓库名.git (push)
upstream  https://github.com/LiuXiYing/IntroToCybersecurityTools.git (fetch)
upstream  https://github.com/LiuXiYing/IntroToCybersecurityTools.git (push)
```

### 2.2 每次提交作业

#### 第一步：同步新题目

```bash
git pull upstream main
```

#### 第二步：阅读作业要求

打开 `homework/LabX/LabX.md`，确认以下内容：

- 作业题目和完成要求
- 要提交的文件数量、文件名和文件类型
- 作业截止时间

文件名和扩展名区分大小写，必须与作业要求完全一致。

#### 第三步：在自己的文件夹内完成作业

作业必须放在自己的“学号姓名”文件夹下，对应的作业文件夹必须命名为 `Lab1`、`Lab2` 等。其中 `L` 必须大写，`ab` 必须小写。

```text
2023010102刘西莹/
└── Lab1/
    ├── stack.c
    └── report.md
```

- `Lab1`：正确
- `lab1`：错误
- `LAB1`：错误

#### 第四步：检查并提交

提交前先检查改动文件列表：

```bash
git status
git diff --name-status upstream/main
```

确认没有修改自己文件夹以外的内容后，再提交并推送：

```bash
git add .
git commit -m "完成Lab1作业"
git push
```

#### 第五步：发起 PR

前往自己 fork 的仓库页面，点击 `Contribute → Open pull request`，向老师仓库的 `main` 分支发起 PR。

PR 标题格式：

```text
[学号姓名]LabX作业提交
```

PR 描述可以填写完成思路或遇到的问题：

```markdown
## 说明

（选填，填写思路或遇到的问题）
```

PR 发出后如果发现问题，直接在本地修改并再次 `push`，原 PR 会自动更新，不需要重新发起。 误删、误改或误拖动文件时，按 [7.1 节](#71-已经-push-并提交-pr)恢复。

### 2.3 跳交作业

如果某次作业没有提交，之后想直接提交下一次作业，例如没有交 Lab3、准备提交 Lab4，请删除**自己文件夹中未提交的 Lab3 内容**，只保留本次要提交的 Lab4 内容后再发起 PR。

只能删除自己文件夹内未提交的作业。不能删除 `homework/` 中的题目、其他同学的文件，或自己以前已经提交的作业。

### 2.4 作业截图

如果作业要求提交运行结果或其他截图，必须使用电脑自带的截图功能，保证文字清楚、内容完整，并适当裁剪无关区域。

> **严禁使用手机拍摄电脑屏幕代替截图。** 手机拍屏容易出现反光、摩尔纹、画面倾斜和文字模糊，不符合提交要求。

## 3. PR 合并验收规范

以下规则用于判断 PR 是否可以合并。任何一项阻止合并的问题都需要先修改，再重新检查。

### 3.1 PR 标题

标题格式为：

```text
[学号姓名]LabX作业提交
```

具体要求：

- 中括号必须使用英文方括号 `[]`。
- “学号姓名”必须由 10 位数字学号和姓名组成，中间不能有空格。
- `LabX` 必须是大写 `L`、小写 `ab` 和数字编号。
- 标题区分大小写。
- 英文右方括号 `]` 与 `LabX` 之间不能有空格。

| 标题 | 结果 | 说明 |
| --- | :---: | --- |
| `[2023010102刘西莹]Lab1作业提交` | ✓ | 格式正确 |
| `[2023010102刘西莹] Lab1作业提交` | ✗ | 右方括号后存在空格 |
| `【2023010102刘西莹】Lab1作业提交` | ✗ | 使用了中文括号 |
| `[2023010102刘西莹]lab1作业提交` | ✗ | `Lab` 大小写错误 |

### 3.2 学生文件夹

- 位置：仓库根目录。
- 命名格式：10 位数字学号 + 姓名。
- 正确示例：`2023010102刘西莹`。
- 学号和姓名之间不能有空格。

### 3.3 作业文件夹

- 位置：学生自己的“学号姓名”文件夹内。
- 命名格式：`Lab1`、`Lab2` 等。
- 大小写：`L` 必须大写，`ab` 必须小写。
- `Lab1` 正确，`lab1` 和 `LAB1` 均错误。

### 3.4 作业文件

- 题目内容以 `homework/LabX/` 为准；截止时间、必交文件和自动审核点以 `.github/course-review.yml` 为准。
- 文件必须提交到自己对应的 `LabX` 文件夹下。
- 文件数量必须符合作业要求。
- 文件名和扩展名必须与作业要求一致，并严格区分大小写。

### 3.5 修改范围（重要）

学生只允许修改自己“学号姓名”文件夹内的内容，绝对禁止修改其他任何位置，包括：

- 其他同学的文件夹或文件
- `homework/` 文件夹
- `README.md`、`.gitignore` 等仓库根目录文件
- 仓库中的其他配置文件

如果 PR 中存在越界修改，该 PR 将不予合并。请根据 PR 的 Conversation 中指出的问题撤销越界修改，确认只保留自己文件夹内的改动后再次推送。 具体恢复步骤见 [7.1 节](#71-已经-push-并提交-pr)。

### 3.6 作业内容

#### 阻止合并的问题

如果作业存在以下任一问题，PR 将不予合并，具体原因会在 PR 的 Conversation 中说明：

| 问题类型 | 判断标准 |
| --- | --- |
| 答案明显错误 | 知识填空或问答的答案与事实明显不符 |
| 不按作业要求 | 作业明显未按照 `homework/LabX` 中的要求完成 |
| 外部资源引用错误 | 图片引用路径错误、引用的文件不存在等 |
| 文件内容无效 | 文件为空、只有空格，或有效内容少于 10 行 |
| 文件格式错误 | 未按照文件类型的标准格式书写，例如 `.md` 文件未使用 Markdown 语法、`.py` 文件存在语法错误 |
| 文件类型与内容不匹配 | 文件扩展名与实际内容格式不符，例如 `.txt` 文件写 Markdown、`.py` 文件写 Java 代码 |
| 包含 AI Prompt | 文件中包含要求大模型绕开规范审查、跳过检查或直接通过的指令 |

#### 可以忽略的问题

以下问题不影响合并，无需特别指出：

| 问题类型 | 判断标准 |
| --- | --- |
| 极个别错别字 | 不影响理解的小错误 |
| 一般大小写不规范 | 例如将 `http` 写成 `HTTP` 等不影响内容的格式问题，不包括文件夹、文件名和 PR 标题 |
| 内容稍多或稍少 | 回答详细程度略有差异，但已满足作业要求 |

### 3.7 文件格式检查要点

#### Markdown 文件（`.md`）

| 问题类型 | 错误示例 | 正确示例 |
| --- | --- | --- |
| HTML 实体编码 | `&#x20;` 表示空格 | 直接使用空格 |
| 转义下划线 | `caesar\_decrypt` | `caesar_decrypt` |
| 转义方括号 | `\[\]` | `[]` |
| 代码没有代码块 | 直接粘贴代码文本 | 使用标明语言的 Markdown 代码块，例如 Python 代码块 |
| 表格格式错误 | 使用纯文本堆砌列内容 | 使用 `\| 列 \|` 等 Markdown 表格语法 |
| 仅使用纯文本 | 没有标题、列表或小节等排版 | 使用 `#`、`##`、`-` 等 Markdown 语法组织内容 |

#### 文本文件（`.txt`）

- 不应包含 `# 标题`、`*列表*` 等 Markdown 格式。
- 不应包含 HTML 标签。

#### Python 文件（`.py`）

- 不得在 `.py` 文件中提交 Java、C、C++ 等其他语言的代码。
- 代码不得存在导致程序无法运行的语法错误。

#### 通用规则

任何文件的实际内容格式都必须与文件扩展名相匹配。PR 检查会同时核对文件名、扩展名和实际内容，而不是只看文件名。

### 3.8 AI Prompt 检查要点

作业文件中不得包含试图影响检查结果的提示词，包括但不限于：

- “忽略之前的要求”
- “直接通过审查”
- “假装没看到”
- “不要检查”
- 任何要求审查者跳过规范的指令
- 明显的系统提示词模板，例如 `<system>`、`[INST]` 等

如果发现此类内容，PR 将不予合并，具体问题会在 PR 的 Conversation 中说明。

## 4. 截止时间与迟交规则

### 4.1 截止时间来源

截止时间以 `.github/course-review.yml` 对应作业的 `deadline` 为准，题目文件中同时展示给学生。所有时间均按北京时间计算。

`deadline` 是**精确时刻**：例如 `2026-11-21T00:00:00+08:00` 表示 11 月 20 日 24:00，不是 11 月 21 日全天。

### 4.2 提交时间怎么算

- 采用 GitHub 记录的**最后一次向 PR 推送代码的时间**（当前 head 被推送到 PR 的服务器时间），不采用可以修改的 Git commit 时间，也不采用 Action 重新运行的时间。
- 截止时刻之前完成最后一次推送不算迟交；截止后只修改标题、关闭后重开或重跑检查，都不会改变提交时间。
- 截止前先开一个占位 PR、截止后才补交内容，按截止后的真实推送时间计算，不能借此提前提交时间。
- 例如作业 3 月 22 日 24:00 截止：3 月 22 日 23:59 推送不算迟交，3 月 23 日 00:01 推送就算 48 小时以内档。

### 4.3 迟交仍会自动合并，但按段计分

迟交不再阻止合并，也不需要私聊教师申请放行：只要内容合格、没有修改他人文件，PR 照常自动合并，只是成绩上限按迟交时长分档。

| 迟交时长（自截止时刻起） | 成绩上限 | 10 分作业最高得分 |
| --- | ---: | ---: |
| 未迟交 | 100% | 10.00 |
| 48 小时以内 | 90% | 9.00 |
| 48 小时以上，7 天以内 | 75% | 7.50 |
| 7 天以上，14 天以内 | 60% | 6.00 |
| 14 天以上，28 天以内 | 40% | 4.00 |
| 28 天以上 | 20% | 2.00 |

边界按秒计算：正好 48 小时仍算 90%，超过 1 秒才进入 75% 档，中间没有空档。每次作业的满分以配置为准，不一定都是 10 分。

成绩由程序按上述规则计算并写入仓库的 `grades` 分支，PR 评论中会列出有效提交时间、迟交时长、分档和本次得分。

### 4.4 48 小时修正期

截止之前在**同一个 PR** 中推送过完整作业（必交文件齐全、内容不是模板复制、截图不是空白占位）时，如果内容检查发现问题，可以在截止后 48 小时内改正并重新推送，仍按 100% 计分。

以下情况不享受修正期，按实际迟交档计分：

- 截止前只开了空 PR，或只提交了空文件、模板副本、空白截图；
- 修正超过 48 小时；
- 截止前没有推送过任何实质性内容。

### 4.5 各作业的计分模式

`Lab1` 至 `Lab7` 在本规则上线前已经发布，标记为 `legacy`：**不实行分段迟交计分**，内容合格即自动合并，评论中不会显示虚构的满分。是否计入课程成绩以教师原有规则为准。

`Lab8` 及之后发布的作业使用 `tiered`，执行第 4.3 节的迟交分档和第 4.4 节的 48 小时修正期。迟交不影响内容审核与自动合并，只影响成绩上限。

### 4.6 不需要私聊教师

普通迟交无需说明，系统会自动按规定计分。只有两种情形需要联系教师：内容检查指出的问题无法自行修改，或怀疑系统判定的时间、分数有误。

## 5. PR 自动检查与合并流程

本仓库使用固定版本的共享审核器 **Course PR Reviewer 0.15.2**。GitHub Actions 负责触发检查、账号映射、确定性规则、评论、合并和成绩记录；GLM 与 Gemini 共同审核文本和图片。两个模型意见不一致时最多审核三轮，达到上限仍有分歧时，该 AI 阶段按共享审核器规则视为通过，其他检查仍须全部通过；结果不确定或服务异常时暂停合并。PaddleOCR 已停用。学生不需要手动启动检查。

### 5.1 自动检查的触发

发起 PR 或向该 PR 再次推送修改后，自动检查都会运行。检查期间请留意 PR 的 Conversation 和检查状态。

如果检查未通过，请按照 Conversation 中指出的问题修改作业并再次 `push`。新的提交会触发新一轮检查，不需要关闭或重新发起 PR。

### 5.2 自动检查顺序

系统按照以下顺序处理 PR：

1. 读取 PR 的标题、作者、当前 head SHA 及其推送时间和全部变更文件。
2. 根据 `.github/students.yml` 确认 GitHub 账号对应的学号和姓名。
3. 检查 PR 标题是否符合 `[学号姓名]LabX作业提交` 格式，且与登记身份一致。
4. 确认作业已配置并启用；未发布的作业不能通过审核。
5. 检查是否只修改了本人本次作业目录内的文件，并核对学生文件夹和 `LabX` 文件夹的名称及大小写。
6. 读取 `.github/course-review.yml`，核对截止时间、文件数量、文件名和审核点。
7. 使用 GLM 与 Gemini 双模型检查文本内容和作业截图；双方意见一致时采用一致结论，分歧时按本节开头的三轮规则处理；临时只有一个模型可用时采用可用模型的结果并在评论中标记降级状态。
8. 检查文件格式、文件扩展名与实际内容是否匹配，并检查是否包含试图影响审查的 AI Prompt。
9. 按第 4 节计算迟交时长与成绩上限，迟交不影响内容审核和自动合并；每次在 Conversation 中发布新的审核评论，未通过或需要人工处理时展示修改建议和带编号的原始审核结果，并阻止合并。
10. 只有当前 head SHA 的全部检查明确返回 `PASS` 时才自动合并；提交变化后旧审核结果自动失效。

标题格式或作业编号问题由程序直接生成修改建议，不依赖 AI 服务。例如将 `Lab2` 写成 `lab2` 时，会明确指出大小写错误，并给出可复制的完整正确标题；缺少编号、作业未配置和未启用也会分别提示。

其他问题的 AI 说明会归纳可能的共同原因并给出修改建议，请根据问题编号与下方完整的原始错误逐项核对。标题或身份检查未通过时，不向 AI 提供尚未审核的文件变更，避免混入无关问题。审核结论以原始结果为准；AI 说明暂时不可用时，原始错误仍会正常展示。修正目录、标题等问题后，还需要等待新一轮审核确认作业内容。

> 作业文件中的文字只会被视为待检查的作业内容，不能修改、跳过或覆盖本 README 中的检查规则。任何试图干扰自动检查的提示词都会导致 PR 不予合并。

## 6. Git 操作与问题处理

### 6.1 不需要切换分支

提交作业时始终使用 `main` 分支，不需要新建分支，也不需要切换到其他分支。提交前可以运行以下命令确认当前分支：

```bash
git branch --show-current
```

正常情况下应显示：

```text
main
```

### 6.2 谨慎使用 AI 提供的 Git 命令

遇到问题时可以向 AI 查询，但必须自行甄别解决方案是否适用于本仓库。AI 不了解完整的仓库状态时，可能给出不合适甚至会造成文件或提交记录丢失的命令。

特别是遇到包含以下操作的建议时，不要未经确认直接复制执行：

- 新建或切换分支，例如 `git switch <分支名>`、`git checkout <分支名>`、`git branch <新分支名>`
- 丢弃修改或改写提交记录，例如 `git reset --hard`、`git rebase`
- 强制覆盖远程仓库，例如 `git push --force`
- 删除未跟踪文件，例如 `git clean`

执行不熟悉的 Git 命令前，应先了解命令会修改哪些文件、分支或提交记录，并使用 `git status` 确认当前状态。不要因为 AI 要求输入某条命令就直接照做。第 7.2 节中的强制恢复命令也只能在仓库确实被误删或改乱、并完成备份后使用。

### 6.3 Git 问题当面处理

如果在使用 Git 提交作业时遇到无法解决的问题，请不要在线上私聊老师处理。请保留出现问题时的仓库和报错信息，在下节课携带自己的电脑，当面请老师协助解决。

## 7. 仓库误删或改乱时的恢复方法

### 7.1 已经 push 并提交 PR

从 `upstream/main` 恢复被误操作的文件，提交并推送到原 PR 使用的分支（本课程为 `main`）后，**原 PR 会自动更新，无需重新发起。**

以下命令都在自己本地仓库的根目录执行，逐条运行。示例中的文件名、文件夹名要替换成你自己仓库里的真实路径，先运行 `git status` 就能看到真实路径。

> **引号不用输入。** 命令里的引号只是为了标出“这一段是路径”，替换时直接写路径本身，前后什么都不要加。本课程的文件路径都不含空格，不需要引号；如果确实想加，只能用**英文半角** `"`。用中文引号 `“ ”`，或者把引号当成路径的一部分，都会报 `pathspec ... did not match`。

例如要恢复被误改的同学文件 `2026010002李四/Lab1/Lab1.md`，正确写法只有下面这一种：

```bash
git restore --source=upstream/main -- 2026010002李四/Lab1/Lab1.md
```

下面各节里的 `被删的文件夹名`、`被改的文件名`、`同学的文件夹名`，都照这个样子替换。

先检查当前状态：

```bash
git status
```

确认当前分支是 `main`，并先处理好其他尚未提交的改动。再获取老师仓库的最新内容：

```bash
git fetch upstream
```

`git fetch` 只更新老师仓库的引用，不会直接修改本地文件。下面按自己的误操作情况选择对应步骤；`git restore` 会把指定路径恢复为老师仓库中的版本，执行前请核对路径。

#### ① 误删了同学的文件夹或 homework

把下面两处 `被删的文件夹名` 都替换成被删掉的那个文件夹名：同学 `2026010001张三` 的文件夹被删，就写 `2026010001张三`；误删了 `homework/`，就写 `homework`。

```bash
git restore --source=upstream/main -- 被删的文件夹名
```

```bash
git add -- 被删的文件夹名
```

```bash
git commit -m "恢复误删的文件"
```

```bash
git push origin main
```

#### ② 改动了他人的文件

文件名要填写相对于仓库根目录的完整路径，例如 `2026010002李四/Lab1/Lab1.md`；误改了根目录的 `README.md` 等文件时，也可按本组步骤恢复对应文件。

```bash
git restore --source=upstream/main -- 被改的文件名
```

```bash
git add -- 被改的文件名
```

```bash
git commit -m "恢复误改的文件"
```

```bash
git push origin main
```

#### ③ 把同学的文件夹拖进了自己的文件夹

先恢复被拖走的同学文件夹到原位。例如同学是 `2026010001张三`，就把 `同学的文件夹名` 替换成 `2026010001张三`：

```bash
git restore --source=upstream/main -- 同学的文件夹名
```

再删除自己文件夹里误拖入的部分。确认下面的路径指向**误拖入的同学文件夹**：两个名字都用真实的文件夹名替换，中间用 `/` 连接，例如自己的文件夹是 `2026010002李四`、拖进来的是 `2026010001张三`，就写成 `2026010002李四/2026010001张三`：

```bash
git rm -r -- 自己的文件夹名/同学的文件夹名
```

`git rm` 已暂存这部分删除；接着暂存恢复到原位的文件夹：

```bash
git add -- 同学的文件夹名
```

```bash
git commit -m "恢复误操作"
```

```bash
git push origin main
```

推送后回到原 PR 的 **Files changed** 页面，确认误删、误改的内容已恢复，误拖入的文件已移除，并且只剩本次作业允许的改动。等待自动审核重新运行即可。

### 7.2 需要整体恢复仓库（谨慎使用）

如果整个仓库已经无法正常同步，且确实需要整体恢复，在备份个人作业后，可以让自己仓库的 `main` 分支重新以老师仓库的 `main` 分支为准：

```bash
git fetch upstream
git reset --hard upstream/main
git push origin main --force
```

三条命令的作用分别是：

1. `git fetch upstream`：获取老师仓库的最新内容，不直接修改本地文件。
2. `git reset --hard upstream/main`：把本地 `main` 分支及其中受 Git 管理的文件强制恢复成老师仓库的状态。
3. `git push origin main --force`：强制更新自己 GitHub 仓库中的 `main` 分支，使其与本地恢复后的状态一致。

> **危险：后两条命令会丢弃内容和提交记录。** 凡是还没有合并进老师仓库、也没有另行备份的个人作业，都可能被删除，而且很难恢复。执行前必须先运行 `git status` 检查当前分支和修改，并把仍需保留的文件复制到仓库外备份。不要把这三条命令当作日常同步命令；只有确实需要恢复仓库时才使用。

恢复完成后，再把本次要提交的作业复制回自己的文件夹，重新提交并推送。不要复制或修改其他同学的文件。

## 8. 提交前最终检查

发起 PR 前，请逐项确认：

- 已同步老师仓库的最新内容。
- PR 标题、学生文件夹和 `LabX` 文件夹命名正确。
- 文件数量、文件名、文件类型和内容符合作业要求。
- 只修改了自己的文件夹，没有删除或改动其他位置的内容。
- 要求提交的截图均由电脑截图工具生成，画面清晰完整。
- 已使用 `git status` 和 `git diff --name-status upstream/main` 检查变更文件。
- 作业未超过截止时间。
